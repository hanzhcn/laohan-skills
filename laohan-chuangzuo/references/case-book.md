# 否稿与改稿案例库

用途：把 Jeffrey 的真实否稿、改稿与看片裁决整理成**带条件的判断案例**，写清"为何这样改、换条件怎么办、哪些用法会错"，代替无限堆禁令。修稿或优化 skill 时先查本库：新情况若与某案例条件吻合，按该案例的判断走；条件不同，按案例里"换条件怎么办"的边界推理，不机械套用结论。

登记规则：Jeffrey 否稿、改稿意见或看片反馈出现时，由当轮 skill 登记（背景/原判断/Jeffrey 裁决原文要点/归因/边界各一段），必须注明来源（episode、日期或规则修订记录）；没有真实来源不登记，模型自评不算案例。

## 案例 1：口头禅的准与不准

- **背景**：口播稿互动判断与无奈收口的表达选择。
- **裁决**（Jeffrey 明确表态，2026 年规则化）：互动判断只用"是不是有点意思"；无奈收口用"这一天天的"；"这个可有点意思"和"可有点意思"永久禁用。
- **为何这样改**：前两句是 Jeffrey 真实会说的口头禅，念着是他；后两句他不这么说，出现在稿里就是 AI 编的"人味"。
- **换条件怎么办**：其他口头禅候选按同一判据过——Jeffrey 真实说过且语境贴合才可用，没听他说过的一律不用。
- **哪些用法会错**：把禁用两句"改写近似版"绕开禁令（如"这可真有点意思"）——禁的是"Jeffrey 不这么说话"这件事，不是两个字符串。

## 案例 2：停更/回归/产品开发题的开场

- **背景**：停更回归、产品开发类选题的首段写法，早期出现过"我不是偷懒"式自证和无名词的"干脆做了一个"。
- **裁决**（2026-07 规则化）：继承"问题先行四问开场"——观众问题 → 停更动机 → 可信行动 → 产物定义；首段必须说清解决什么、为什么停更、做了什么、产品是什么。
- **为何这样改**：观众第一关心的是"这条和我有什么关系"，不是作者的处境；自证式开场把顺序倒了。
- **换条件怎么办**：仅适用于停更/回归/产品开发题；常规选题照走默认签名开场"嘿，你有没有这种感觉，"，不套四问。
- **哪些用法会错**：在普通教程稿里硬塞"停更动机"；四问答完却始终不出现具体产物名词（钩子不完整）。

## 案例 3：正文之外必须带发布信息

- **背景**：早期口播稿交付即止，标题与视频介绍靠发布时现想。
- **裁决**（laohan-chuangzuo 1.8.0 起）：每份最终口播稿正文后必须附`## 抖音发布信息`：3 个候选标题按判据选 1 个主推并登记理由，视频介绍按观点型/教程型公式生成，末尾标签必含`#AI新星计划`。
- **为何这样改**：标题是钩子的最后一次兑现，脱离正文现想必然走样；候选制防止第一个想到的标题直接上场。
- **换条件怎么办**：该区域不进 TTS/口播，但必须由 `publish_copy_contract` 和整稿 SHA 绑定——正文改动后发布信息同步重估。
- **哪些用法会错**：只附 1 个标题无候选；标题承诺正文兑现不了；忘记 `#AI新星计划` 标签。

## 案例 4：机械 PASS 救不了节奏

- **背景**：skills 篇成片（2026-10-26）：全链机械门（validator、合同检查）通过，Jeffrey 看片后裁定节奏太慢。
- **裁决**：按此前已约定的加速规则产出加速版成片再定稿；不看机械 PASS 挡驾。
- **为何这样改**：机械门验证的是合同字段与结构完整性，节奏是看片才能判的观感维度，两者不互相覆盖。
- **换条件怎么办**：机械门失败当然先修门内问题；本案的边界是"门全绿仍可能被否"，不是"门没用"。
- **哪些用法会错**：拿"所有检查 PASS"回应 Jeffrey 的观感否稿；或反过来把本案扩大成"机械门都不用跑"。
